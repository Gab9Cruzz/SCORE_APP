## Problem Statement

El backend de Score-App (FastAPI + Postgres) está completo: 11 routers, auth JWT
con roles (Admin/Árbitro/Público), triggers de validación de dominio, vistas
agregadas de estadísticas. La carpeta `frontend/` está vacía — cero líneas de
código. No existe forma de que un humano use el sistema. Esta fase construye
las primeras 3 pantallas para probar que el API funciona de punta a punta:
Dashboard de Torneo, Control de Mesa, y Partido en Vivo / Vista Pública.

## Demand Evidence

Ninguna validada todavía. No hay una liga, grupo o persona específica que haya
pedido esto o esté esperando usarlo esta semana. El proyecto se financia hoy
con el interés del fundador en construirlo, no con dolor de un usuario
identificado.

## Status Quo

Organizadores de torneos amateur chicos (liga barrial, oficina, amigos) hoy
usan planillas de Excel/Sheets + coordinación por WhatsApp. Costo real:
errores de cálculo en la tabla de posiciones, actualizaciones tardías, nadie
tiene visibilidad en vivo del estado de un partido. Esto es dolor genuino,
pero también es el dolor que ya resuelven Challonge, Toornament, Brakto,
TeamSnap y media docena de herramientas más — el terreno está ocupado por
motores de brackets, sobre todo esports.

## Target User & Narrowest Wedge

Todavía no hay una persona nombrable. La categoría más cercana sería "el
organizador de una liga amateur de fútbol" (no bracket de eliminación —
round-robin con tabla de posiciones), pero sin un nombre concreto. El wedge
real candidato: a diferencia de las herramientas genéricas del mercado, el
dominio ya modelado (Torneo → Equipo → Partido, catálogo de eventos
Gol/Autogol/Tarjeta Amarilla/Tarjeta Roja/Cambio, triggers de vigencia de
jugador en plantilla) es fútbol de liga verticalizado, no brackets genéricos.
Ese wedge solo se valida si aparece una liga real dispuesta a usarlo.

## Constraints

- Backend 100% construido y no requiere cambios para estas 3 pantallas.
- Sin autenticación de terceros — JWT propio ya implementado (`/auth/login`,
  `/auth/me`), roles Admin / Arbitro / Publico.
- `/estadisticas/*` es público, sin auth — es lo que ve cualquier espectador.
- Sin WebSockets en el backend — "en vivo" se resuelve por polling.
- Deploy y hosting de producción quedan fuera de esta fase.
- Windows como entorno de desarrollo (el backend ya documenta particularidades
  de driver de Postgres en Windows — no aplica al frontend pero es contexto
  del entorno).

## Premises

1. El problema correcto en esta fase es probar que el API funciona de punta a
   punta con 3 pantallas reales, no agregar features al backend. — Acordado.
2. El riesgo real no probado es la usabilidad de Control de Mesa en vivo (¿un
   árbitro puede cargar un gol rápido desde el celular?), no las pantallas
   CRUD. — Acordado.
3. Esta fase es frontend puro — el backend ya cubre el 100% de lo necesario
   (auth, roles, datos) para las 3 páginas. — Acordado.
4. Deploy/hosting de producción queda fuera de esta fase; el objetivo es
   correrlo local y validar que funciona. — Acordado.
5. No hay evidencia de demanda validada todavía — esto se construye para
   tener algo mostrable a una liga real, no porque una liga real ya lo
   pidió. — Acordado.

## Approaches Considered

### Approach A: Minimal viable
Vite + React + React Router, `fetch` con wrapper delgado, JWT en
`localStorage`, polling con `setInterval` en Partido en Vivo. Rechazado:
ya dentro de estas mismas 3 páginas, Dashboard, Control de Mesa y Partido
en Vivo comparten el mismo problema — pedir datos, mostrar loading/error, y
reaccionar a un 401/403 — y sin una capa de estado de servidor ese código
se escribe 3 veces a mano en esta fase, no en una hipotética página futura.

### Approach C: Creative/lateral — componente compartido por rol
Un solo árbol de componentes "partido en vivo" (marcador + timeline)
reutilizado entre Control de Mesa y Partido en Vivo, condicionado por rol.
Rechazado por esta fase: acoplar dos audiencias (mesa de control vs.
espectador) en un componente compartido arriesga servir mal a ambas — la
mesa necesita formularios densos y rápidos, el público necesita algo visual
y liviano. Queda como candidato a revisar más adelante si la duplicación
entre páginas se vuelve un problema real.

## Recommended Approach

**Approach B: Ideal architecture.** Vite + React + React Router + TanStack
Query para estado de servidor (cache, refetch automático — resuelve el
polling de Partido en Vivo con una línea, `refetchInterval`, arrancando en
5s y ajustando según se sienta en la práctica) + cliente API tipado generado
con `openapi-typescript` a partir de `/openapi.json` que FastAPI ya expone
(script `npm run gen:api`, se corre a mano contra el backend local corriendo
— no en cada build) + un `AuthContext` liviano que expone: usuario actual,
rol, token, y funciones `login()`/`logout()`.

Elegido, con dos razones distintas y ninguna depende de crecimiento futuro
no validado: (1) es un problema de HOY, no de después — el cliente tipado
detecta en compilación cualquier desalineación entre lo que el frontend
manda/lee y lo que el schema de Pydantic espera, contra 11 routers reales,
que es exactamente el riesgo de "conectar la API con React" en esta fase.
(2) si además sigue creciendo, la inversión no se tira. Pero el punto (1) ya
la justifica sin asumir nada sobre demanda futura.

**Manejo de sesión y roles (frontend):**
- Token JWT en `localStorage`; al expirar (401 de cualquier request), el
  `AuthContext` limpia la sesión y redirige a login — sin refresh token en
  esta fase.
- Rutas: `/control-de-mesa` requiere rol Admin o Arbitro — un usuario sin
  sesión o con rol Publico que navega ahí ve una pantalla de "necesitás
  iniciar sesión con un rol autorizado", no un 401 crudo. `/dashboard` y
  `/partido/:id/en-vivo` no requieren login: `/dashboard` lee `GET
  /torneos` y `GET /estadisticas/torneos/{id}/...`, ninguno de los dos
  requiere auth en el backend (confirmado en `routes/torneos.py` —
  `require_roles` solo está en POST/PATCH/DELETE, no en los GET); mismo
  caso para `/estadisticas/*` que usa `/partido/:id/en-vivo`.
- Edición concurrente en Control de Mesa (dos árbitros, o Admin + Árbitro,
  actuando sobre el mismo partido): sin resolución de conflictos en esta
  fase — last-write-wins, cada mutación exitosa dispara un refetch de
  TanStack Query para que la vista se actualice con el estado real del
  servidor. Se revisita si en la práctica genera choques.
- Errores 400 (triggers de Postgres) se muestran como mensaje inline junto
  al formulario de carga de evento, usando el texto que devuelve el backend
  — no una alerta genérica. **Pre-chequeo antes de implementar:** confirmar
  que `exceptions/handlers.py` devuelve el mensaje del trigger en un campo
  `detail` parseable (no el texto crudo de Postgres) — si no lo hace,
  ajustar el handler es un cambio de backend menor, no cubierto por la
  Constraint de "sin cambios al backend", y hay que decidirlo explícitamente
  antes de construir la UI de error.
- El flujo de Cambio (sustitución) necesita saber quién está "en cancha"
  (titulares vigentes, descontando salidas y expulsiones previas en el
  mismo partido) para armar la lista de "quién sale". **Pre-chequeo antes
  de implementar:** ningún endpoint devuelve ese estado derivado hoy —
  confirmar si se calcula en el cliente a partir de `GET
  /eventos-partido?partidos_id=X` (titulares iniciales menos salidas/rojas
  ya cargadas) o si hace falta un endpoint nuevo. Si hace falta endpoint
  nuevo, es la única excepción posible a "esta fase es frontend puro" y se
  decide antes de construir esta pantalla, no durante.

## Success Criteria

- Dashboard de Torneo: lista torneos activos, tabla de posiciones y
  goleadores de un torneo elegido, usando datos reales del backend.
- Control de Mesa: un usuario Admin o Árbitro autenticado puede ver un
  partido y cargar eventos desde un navegador de celular (no solo desktop —
  es el escenario real de uso en cancha). Goles y tarjetas: elegir jugador
  y tipo de evento, 2-3 toques, sin tipear. Cambios: un flujo de 2 pasos
  (elegir quién sale de una lista de titulares en cancha, elegir quién
  entra de una lista de suplentes), tampoco requiere tipear — más pasos que
  un gol porque son dos jugadores, pero cada paso es un toque sobre una
  lista, no un formulario. En todos los casos, la lista de eventos y el
  marcador se actualizan vía refetch inmediatamente después de cada carga
  exitosa, y los 400 de los triggers de Postgres se muestran como error
  legible junto al formulario (no una alerta genérica ni el texto crudo de
  Postgres).
- Partido en Vivo / Vista pública: cualquiera, sin login, ve el marcador y
  la timeline de eventos de un partido, actualizándose sin recargar la
  página.
- Las 3 páginas corren localmente contra el backend real, no contra mocks.

## Distribution Plan

Web service — no aplica empaquetado ni distribución para esta fase (deploy
queda explícitamente fuera de alcance, ver Premisas #4).

## Dependencies

Ninguna — el backend ya expone todo lo necesario. Bloqueante potencial:
Postgres corriendo localmente (`torneos_mvp`) para que el backend responda.
Acoplamiento a tener presente: generar el cliente tipado (`npm run
gen:api`) requiere el backend corriendo con `/openapi.json` accesible — si
se corre contra un backend desactualizado u offline, el cliente queda
desincronizado hasta la próxima generación manual.

funcionando a una liga o grupo real (aunque sea informal — la liga de la
oficina, un grupo de amigos que arma torneos) y mirá qué hacen sin ayudarlos.
Eso convierte la Premisa 5 (sin demanda validada) en evidencia real antes de
seguir construyendo pantallas nuevas.

## What I noticed about how you think

- Dijiste "primero tengamos estas tres páginas funcionando correctamente" —
  eso es secuenciar bien: probar el camino completo antes de expandir a más
  pantallas. No es impaciencia, es orden de validación correcto.
- El backend que ya construiste tiene detalles que la mayoría se salta en un
  MVP: eventos que se anulan en vez de borrarse (auditoría), triggers que
  validan que un jugador realmente pertenecía al equipo en esa fecha. Eso es
  cuidado por los casos borde antes de que alguien te los reclame.
- Cuando te pregunté por el usuario específico dijiste directamente "todavía
  no hay una persona nombrable" en vez de inventar una. Esa honestidad es lo
  que hace que "El Assignment" de arriba tenga sentido — vas a buscar esa
  persona en vez de asumir que existe.
