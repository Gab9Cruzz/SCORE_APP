## 0A. Premise Challenge

1. **¿Es el problema correcto?** Parcialmente reencuadrable. El pedido se lee como "4 áreas
   separadas" pero 3 de los 6 puntos (filtrado estricto de suplentes, estado mutante en
   cambios, roster date-effective) son la **misma clase de bug**: "¿quién es candidato válido
   ahora mismo?", calculada de 3 formas distintas en 3 lugares del código — correcta en el
   trigger SQL (`fn_validar_jugador_partido`), incorrecta en la vista de convocatoria
   (`vw_jugadores_activos_por_equipo`), e incompleta en la derivación de React
   (`deriveTitularSuplente`/`qbCandidatosSale`). El reencuadre de mayor apalancamiento no es
   "parchear 3 sitios" sino "una sola fuente de verdad para date-effective, los otros dos la
   consumen" — university approach, ver 0C-bis Approach B.
2. **¿Outcome real?** Confianza del operador de mesa en los datos que carga (no puede cargar
   un cambio con la lista de suplentes equivocada, no puede cerrar un resultado sin saber a
   quién le puso la tarjeta) + confianza del árbitro/admin en que el bracket de playoffs no
   requiere reconstruir a mano los cruces. Ninguno de los 4 puntos es una feature especulativa:
   los 3 primeros son bugs de datos incorrectos ya en producción potencial; el 4° es un botón
   que falta conectar (el motor ya existe).
3. **¿Qué pasa si no se hace nada?** El bug de date-effective en convocatorias (punto 3) es
   el único con **riesgo de dato incorrecto ya persistido públicamente** (un jugador que no
   pertenecía al equipo en la fecha del partido, convocado igual) — real, no hipotético, y el
   propio trigger de eventos ya demuestra que el equipo sabe cuál es la regla correcta, solo no
   la aplicó en el lugar de lectura. Los demás son fricción operativa (dropdown con ruido,
   timeline sin nombre, redirect ausente) — dolor real pero no de integridad de datos.

## 0C-bis. Implementation Alternatives

**APPROACH A — Minimal viable (parchear cada síntoma donde aparece)**
  Summary: arreglar `deriveTitularSuplente` con el flag de convocado; agregar `deriveEnCancha`
  en el frontend únicamente (solo `ModalResultadoDirecto`, que es el archivo que el pedido
  menciona); doble-amarilla solo client-side en el batch de resultado directo; el filtro de
  fecha se agrega directo en `plantilla_equipo` (cambiando la vista existente); mover
  `BracketView` con un `import` cruzado sin extraerlo a módulo propio.
  Effort: S (human: ~1 día / CC: ~1-2h)
  Risk: Medio-Alto — cambiar `plantilla_equipo`/la vista rompe los otros callers que
  legítimamente quieren "plantel de hoy" (gestión de equipos, selección de goleador en vivo);
  el double-yellow solo en el modal de resultado directo dejaría el camino EN VIVO
  (`MesaPanel`) sin la regla — inconsistente según qué pantalla use el árbitro.
  Pros: menos archivos tocados, ships rápido.
  Cons: reintroduce exactamente el bug de "3 fuentes de verdad" que la Premisa 1 identificó
  como el problema real; dos usuarios (Árbitro en vivo vs. Admin cargando resultado directo)
  verían comportamiento distinto para la misma regla de negocio.
  Reuses: `deriveHistorialElegibilidad` parcialmente.

**APPROACH B — Ideal architecture (una fuente de verdad, ambos caminos comparten la regla)**
  Summary: `deriveEnCancha` como función pura compartida en `eventos.ts`, usada por
  `ModalResultadoDirecto` Y `MesaPanel` (mismo fix, un solo lugar); doble-amarilla como función
  de módulo server-side (`reglas_tarjetas.py`, mismo patrón que `reglas_cambio.py`), llamada
  desde AMBOS `EventoPartidoService.create` (vivo) y `PartidoService.registrar_resultado_directo`
  (resultado directo) — el cliente solo previsualiza, nunca inserta el evento sintético; el
  filtro de fecha va en un método de repositorio NUEVO (`plantilla_equipo_en_fecha`), sin tocar
  la vista/método existente que otros callers usan correctamente; `BracketView` se extrae a
  componente exportado y se monta en dos tabs sin duplicar lógica.
  Effort: M (human: ~2-3 días / CC: ~3-4h)
  Risk: Bajo — cada cambio es aditivo o de un solo call-site, no reescribe nada que funcione hoy.
  Pros: la regla de negocio vive en un solo lugar por dominio (igual que ya hace
  `reglas_cambio.py`, documentado explícitamente como lección aprendida en este mismo repo);
  cero riesgo de romper callers existentes de `plantilla_equipo`; consistente entre Modo Vivo
  y Resultado Directo — el pedido original explícitamente pide un "listener" (implica
  detección centralizada, no un `if` local a un formulario).
  Cons: más archivos tocados (backend + frontend en ambos caminos de carga de eventos).
  Reuses: patrón `reglas_cambio.py` (server), patrón `derive*` de `eventos.ts` (frontend),
  patrón de vista/repo existente para SQL date-effective (copia el WHERE del trigger).

**RECOMENDACIÓN: Approach B** — DRY (Principio 4) y "root cause, not symptom" (grep de
callers, fix compartido) son reglas explícitas de este mismo proyecto (`reglas_cambio.py`
documenta esa lección textualmente). El Approach A reintroduce el problema que la Premisa 1
identificó. Auto-decidido — Completeness: A=5/10, B=9/10.

## §1. "Estado mutante en cambios" — el hook/derivación pedido (Entregable 1)

batch local (`otrosEventos`). El mismo bug existe en el camino EN VIVO,

**La derivación pura (no un hook con estado — sigue el patrón `derive*` ya establecido en
este archivo, "cálculo puro sobre datos existentes, no una fuente de verdad propia"):**

```ts
// frontend/src/components/eventos.ts — nueva función, junto a deriveHistorialElegibilidad
/** Quiénes están "en cancha" AHORA para elegir en un "Sale": titulares que no
 * salieron/fueron expulsados, MÁS suplentes que ya entraron (y no volvieron a
 * salir). Sin esto, un suplente que entra por un Cambio queda inelegible para
 * un Cambio posterior en el MISMO batch/timeline — el "estado mutante" que
 * pide el pedido (lesiones rápidas, etc.). Compone `salidosOExpulsados` y
 * `yaEntraron` (ya derivados por deriveHistorialElegibilidad) en vez de
 * reimplementar el historial: 1 sola fuente de verdad para ambos ejes de la
 * elegibilidad ("Sale" y "Entra"), igual criterio de polaridad explícita que
 * deriveTitularSuplente. */
export function deriveEnCancha(
  titularesJugadorIds: Set<number>,
  salidosOExpulsados: Set<number>,
  yaEntraron: Set<number>,
): Set<number> {
  const enCancha = new Set(titularesJugadorIds);
  for (const id of yaEntraron) enCancha.add(id);
  for (const id of salidosOExpulsados) enCancha.delete(id);
  return enCancha;
}
```

## §2. Filtrado estricto de suplentes — el bug real (Entregable, parte del pedido #1)

**El bug exacto** está en `deriveTitularSuplente` (`eventos.ts:83-97`): calcula `suplentes`
como "todo el plantel del CLUB que no es titular", no "todo lo CONVOCADO a este partido que no
es titular". Un jugador del club nunca convocado a este partido específico aparece igual en
"Entra".

**¿El backend ya devuelve lo necesario?** Sí — `GET /partidos/{id}/convocados` devuelve una
fila SOLO por jugador efectivamente convocado (`{jugador_perfil_id, titular}`), porque
`CONVOCADO_A_PARTIDO` solo tiene filas para gente convocada. No hace falta un endpoint nuevo
ni un flag nuevo — el bug es que el frontend descarta las filas `titular:false` y le pide a
`deriveTitularSuplente` que "adivine" quién es suplente mirando el plantel completo del club.

**Fix — firma nueva, un parámetro más:**

```ts
export function deriveTitularSuplente(
  convocadosPerfilIds: Set<number>,   // NUEVO: TODAS las filas de GET /convocados (titular+suplente)
  titularesPerfilIds: Set<number>,
  plantilla: PlantillaJugador[],
): { titulares: Set<number>; suplentes: Set<number> } {
  if (convocadosPerfilIds.size === 0) return { titulares: new Set(), suplentes: new Set() };
  const titulares = new Set<number>();
  const suplentes = new Set<number>();
  for (const j of plantilla) {
    if (!convocadosPerfilIds.has(j.jugador_perfil_id)) continue; // no convocado a ESTE partido
    if (titularesPerfilIds.has(j.jugador_perfil_id)) titulares.add(j.jugador_id);
    else suplentes.add(j.jugador_id);
  }
  return { titulares, suplentes };
}
```

Call sites (`ModalResultadoDirecto.tsx:136-147`, `MesaPanel.tsx:174-183,250-253`) agregan una
línea cada uno: `const convocadosPerfilIds = useMemo(() => new Set((convocadosQuery.data ?? []).map((c) => c.jugador_perfil_id)), [convocadosQuery.data]);`
y la pasan primero. `sinConvocatoria` pasa a ser `convocadosPerfilIds.size === 0` (equivalente
hoy, más correcto a futuro).

## §3. Doble amarilla → roja automática (listener)

**Dónde vive la regla — servidor, autoritativo, un solo punto de inserción**, siguiendo el
patrón que este mismo repo ya documenta como lección aprendida

```python

from app.repositories.evento_partido import EventoPartidoRepository


async def procesar_doble_amarilla(
    *,
    evento_partido_repo: EventoPartidoRepository,
    partido_id: int,
    jugador_id: int,
    equipo_id: int,
    eventos_id_amarilla: int,
    eventos_id_roja: int,
    minuto: int,
) -> EventoPartido | None:
    """Listener: si este jugador ya tiene OTRA Tarjeta Amarilla 'Registrada'
    en este partido, autogenera la Tarjeta Roja al mismo minuto. Dedup
    explícito contra rojas ya existentes — si el operador TAMBIÉN carga la
    roja a mano (antes o después), no se duplica (ver riesgo de doble-insert
    en la nota de integración, abajo)."""
    amarillas = await evento_partido_repo.list(
        limit=2, partidos_id=partido_id, eventos_id=eventos_id_amarilla,
        jugador_id=jugador_id, estado="Registrado",
    )
    if len(amarillas) < 2:
        return None
    rojas = await evento_partido_repo.list(
        limit=1, partidos_id=partido_id, eventos_id=eventos_id_roja,
        jugador_id=jugador_id, estado="Registrado",
    )
    if rojas:
        return None
    return EventoPartido(
        partidos_id=partido_id, jugador_id=jugador_id, equipo_id=equipo_id,
        eventos_id=eventos_id_roja, jugador_id_entra=None, minuto=minuto,
    )
```
